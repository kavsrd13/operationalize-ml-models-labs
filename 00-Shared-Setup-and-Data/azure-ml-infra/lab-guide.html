Read this first

Key ideas in three minutes

Infrastructure as code

Instead of clicking in the portal, you describe the resources you want in a text file. The file can be reviewed, versioned in git and deployed again and again with the same result.

Bicep

Microsoft's own language for describing Azure resources. You write .bicep files; Azure Resource Manager reads them and creates the resources.

Desired state

Bicep describes what should exist, not the steps to get there. If a resource already matches, Azure leaves it alone. That is why rerunning a deployment is safe.

Control plane vs data plane

Bicep creates resources (control plane). Putting files into them (data plane) is a separate step with the Azure ML CLI, because Bicep runs inside Azure and cannot read your laptop.

How the pieces connect

You run a script→ It sets your settings→ main.bicepparam reads them→ main.bicep calls 7 modules→ Azure creates resources→ Names saved to .deployment-outputs.json→ Next scripts use them

How resource names are built

Every name follows Microsoft's naming abbreviations. Some names must be unique across all of Azure, so Bicep adds a short suffix from uniqueString(). The same inputs always produce the same suffix, so a second deployment finds the same resources instead of creating new ones.

Preparation

Before you start

  • An Azure subscription where you are Owner, or Contributor + Role Based Access Control Administrator. The template creates role assignments, which plain Contributor cannot do.
  • Visual Studio Code with the Bicep extension by Microsoft (Extensions panel → search "Bicep"). It gives you colour, autocomplete and error checking in .bicep files.
  • Azure CLI 2.61 or newer. Install on Windows with winget install -e --id Microsoft.AzureCLI, then reopen VS Code. Check with az version.
  • PowerShell. Windows PowerShell 5.1 (built into Windows) or PowerShell 7 on Windows, macOS or Linux.
  • The bundled Olist dataset. No separate Kaggle download is needed. From the collection root, run python .\00-Shared-Setup-and-Data\scripts\bootstrap.py --skip-install --skip-azure to extract it.

Know your tools

The project files

Each file has one job. The badge tells you whether you will run it, edit it, or only read it. You do not need to change any file to finish this lab.

infra/ What should exist in Azure (Bicep)
main.bicepRead

The entry point and master plan. It creates the resource group, builds every resource name, and calls the seven modules in the right order.

  • targetScope = 'subscription' lets it create the resource group itself.
  • param lines are the inputs; @allowed and @minLength reject bad values early.
  • output lines hand names and the studio link to the scripts.
main.bicepparamEdit

Your settings: project name, region, VM size, idle shutdown time. This is the file to change if you want different defaults.

  • Each value reads an environment variable first, e.g. AZURE_LOCATION, then falls back to a default.
  • The scripts set those variables from the values you pass them.
bicepconfig.jsonRead

Rules for the Bicep linter, a spell-checker for best practices. For example, it stops you from hard-coding a region or putting a secret in an output.

infra/modules/ One small file per resource
ml-workspace.bicepRead

The Azure ML workspace, the most important resource. It links storage, Key Vault, Application Insights and the registry.

  • Uses a managed identity, so it reaches the other resources without passwords.
  • Storage and Key Vault cannot be swapped after creation.
compute-instance.bicepRead

Your personal cloud computer with Jupyter and VS Code. Only you can use it.

  • Shuts down after 30 idle minutes, and every day at 19:00 UTC.
  • It cannot be safely redeployed, so the deploy script skips it if it already exists.
storage-account.bicepRead

The workspace's default storage for datasets, outputs and notebooks.

  • Data Lake mode is off (Azure ML requires that).
  • Account keys stay on, because compute instances need them.
  • No anonymous public access.
key-vault.bicepRead

A safe for secrets. Azure ML stores keys and connection strings here so they never appear in code.

  • Uses Azure role-based access (RBAC).
  • Deleted vaults are kept for 7 days, the shortest allowed.
container-registry.bicepRead

Stores the Docker images Azure ML builds for environments and model deployments. Basic tier, with the shared admin password turned off.

monitoring.bicepRead

Log Analytics (where logs live, kept 30 days) and Application Insights (monitoring for jobs and endpoints), connected together.

role-assignments.bicepRead

Gives you three roles instead of full Owner rights: AzureML Data Scientist on the workspace, and two Storage Data roles to read data and open notebooks.

data/ What goes into the workspace
olist-data-asset.ymlRead

Defines the data asset olist-ecommerce-raw, version 1: a named, versioned link to your 9 CSV files in Azure.

  • Versions never change. New data means a new version.
  • Jobs refer to it as azureml:olist-ecommerce-raw:1.
scripts/ How and in what order (PowerShell)
00-check-prerequisites.ps1Run

Checks your tools, login, permissions and VM quota. Installs the Azure ML CLI extension if it is missing.

01-validate-infra.ps1Run

Tests the Bicep files and shows a preview of every change. Creates nothing.

02-deploy-infra.ps1Run

Deploys everything, then saves the resource names to .deployment-outputs.json.

03-upload-data.ps1Run

Clean up

10 minutesStops all costsScript 99

Choose one option.

Option A: keep it for the next lab, but stop the compute instance

PowerShell
# Read your compute instance name from the outputs file, then stop it
$ci = (Get-Content .\.deployment-outputs.json -Raw | ConvertFrom-Json).computeInstanceName
az ml compute stop --name $ci --resource-group rg-olist-ml-dev --workspace-name mlw-olist-dev

Option B: delete everything

The script lists what it will delete and asks you to type the resource group name, rg-olist-ml-dev, to confirm.

PowerShell
.\scripts\99-cleanup.ps1 -ProjectName olist

# Afterwards this should print: false
az group exists --name rg-olist-ml-dev
Why not just delete the resource group?

The workspace, Log Analytics and Key Vault are soft-deleted: Azure keeps them hidden for 7–14 days and their names stay reserved. Your next deployment would then fail with "already exists". The cleanup script deletes them permanently.

Self-check

Check your understanding

Answer in your head first, then open the answer.

1. Why does main.bicep use targetScope = 'subscription'?

So the template can create the resource group itself. With resource-group scope, someone would have to create the group by hand first, and part of the environment would not be in code.

2. You ran the deployment twice. Why is there still only one storage account?

Bicep describes the desired state, and the name comes from uniqueString(), which returns the same suffix for the same inputs. Azure finds the existing account with that name and only updates it if something differs.

3. Why is the dataset uploaded by a script instead of by Bicep?

Bicep deployments run inside Azure Resource Manager and cannot read files on your computer. Bicep handles the control plane (creating resources); the Azure ML CLI handles the data plane (uploading content).

4. In the what-if output, what do +, ~ and = mean?

+ means the resource will be created, ~ means it will be modified, and = means no change.

5. You have new Olist data. Can you replace version 1 of the data asset?

No. Data asset versions are immutable. Register version 2 with .\scripts\03-upload-data.ps1 -DataVersion 2. Every experiment then records exactly which data it used.

6. Which file would you change to make the compute instance shut down after 60 idle minutes?

infra/main.bicepparam: set computeInstanceIdleShutdownMinutes = 60. Note that idle shutdown is a creation-time setting, so it applies to a new compute instance.

7. Why does the cleanup script do more than delete the resource group?

Some resources are soft-deleted and keep their names reserved for 7–14 days. The script permanently deletes the workspace and Log Analytics and purges the key vault, so you can deploy again with the same names.

Words used in this lab

Glossary

Subscription
Your Azure account for billing and access. Everything you create belongs to one.
Resource group
A folder for related resources. Delete the group and its contents go with it.
Bicep module
A small Bicep file for one job, called from another Bicep file.
Parameter / output
A value going into a template, and a value coming back out of it.
What-if
A preview of the changes a deployment would make, without making them.
Idempotent
Running it again gives the same result and does not create duplicates.
Managed identity
An identity Azure gives a resource so it can access others without passwords.
Role assignment (RBAC)
Permission for a person or identity to do certain things on a certain resource.
Quota
The maximum number of virtual CPUs you may run per VM family in a region.
Compute instance
A personal cloud workstation with Jupyter and VS Code, managed by Azure ML.
Datastore
A saved connection from the workspace to a storage location.
Data asset
A named, versioned reference to data, such as olist-ecommerce-raw:1.
Soft delete
Deleted, but recoverable for a while, and the name stays reserved.
Control / data plane
Managing resources versus working with the content inside them.
