Key ideas in five minutes

Bicep

Infrastructure as code

You describe the Azure resources in text files. Azure creates exactly what the files say, and running them again changes nothing that is already correct.

workspace

The Azure ML workspace

The home of your ML project. It tracks data, training runs, models and endpoints, and links to storage, a key vault, monitoring and a container registry.

data asset

Versioned data

Your CSV files get a name and a version, olist-ecommerce-raw:1. A version never changes, so every training run records exactly which data it used.

command job

Training in the cloud

Azure ML copies your code to a VM it creates just for the job (serverless compute), runs it, keeps the results and deletes the VM.

MLflow

Experiment tracking

The training script logs settings, metrics, plots and the model with MLflow. Azure ML shows them in studio so you can compare runs.

online endpoint

A model as a web API

An HTTPS address protected by a key. Send it order details as JSON and it returns the predicted shipping cost in under a second.

PART C

Train the model

9

Understand the problem

10 minutesReading

Goal: when a customer checks out, predict the shipping cost (freight_value, in Brazilian reais) of each item. The answer is a number, so this is a regression problem. Every feature must be known at checkout: using anything known only after delivery would be cheating (data leakage).

FeatureWhere it comes fromWhy it helps
distance_kmSeller and customer zip codes → coordinates (geolocation table)Longer trips cost more
product_weight_g, dimensions, volume_cm3Products tableHeavier and bigger parcels cost more
same_state, seller and customer stateSellers and customers tablesShipping inside a state is cheaper
price, product_categoryOrder items and productsExpensive or bulky goods ship differently
items_in_order, items_from_sellerOrder itemsFreight is split across the items in one parcel
purchase_monthOrdersPossible seasonal effects
  • Time-based split. Train on orders before 1 June 2018 (91,231 items), test on June–August 2018 (21,419 items), just as a real model predicts future orders.
  • Log target. A few shipments cost up to R$410 while the median is R$16, so the model learns log(1 + freight) and converts its answer back to reais.
  • Three models are compared: a baseline that always predicts the median, linear (ridge) regression, and gradient boosting.

The feature contract

Load and join seven tables: build_dataset()

The Olist data is spread over linked tables. Starting from order items (one row per item sold), the script adds the purchase date, the customer's and seller's zip codes and states, the product's size and weight, and the English category name.

order_items+ orders+ customers+ sellers+ products+ category names+ geolocation→ 1 row per item
src/train.pylines 85–96
# The geolocation table has many rows per zip-code prefix -> average them.
zip_coords = geolocation.groupby("geolocation_zip_code_prefix")[["geolocation_lat", "geolocation_lng"]].mean()

df = (
    items.merge(orders[["order_id", "customer_id", "order_purchase_timestamp"]], on="order_id")
    .merge(customers[["customer_id", "customer_zip_code_prefix", "customer_state"]], on="customer_id")
    .merge(sellers[["seller_id", "seller_zip_code_prefix", "seller_state"]], on="seller_id")
    .merge(products, on="product_id", how="left")
    .merge(translation, on="product_category_name", how="left")
)
df = df.join(zip_coords.add_prefix("customer_"), on="customer_zip_code_prefix")
df = df.join(zip_coords.add_prefix("seller_"), on="seller_zip_code_prefix")
  • merge(..., on="order_id") works like a SQL JOIN. how="left" keeps an item even if its product has no category.
  • The geolocation table has about a million rows, many per zip code, so the script averages them first. It then attaches the coordinates twice: once for the customer and once for the seller.

Engineer the features

Raw columns become signals the model can learn from.

src/train.pylines 99–117 (condensed)
df["distance_km"] = haversine_km(
    df["seller_geolocation_lat"], df["seller_geolocation_lng"],
    df["customer_geolocation_lat"], df["customer_geolocation_lng"],
)
df["volume_cm3"] = df["product_length_cm"] * df["product_height_cm"] * df["product_width_cm"]
df["same_state"] = (df["seller_state"] == df["customer_state"]).astype(int)
# Freight is charged per seller shipment and split across its items, so the cart matters.
df["items_in_order"] = df.groupby("order_id")["order_item_id"].transform("size")
df["items_from_seller"] = df.groupby(["order_id", "seller_id"])["order_item_id"].transform("size")
df["purchase_month"] = df["purchase_timestamp"].dt.month
df[NUMERIC] = df[NUMERIC].astype("float64")
  • Haversine distance is the straight-line distance between two points on a sphere (the Earth, radius 6,371 km). It is the strongest feature of all.
  • groupby(...).transform("size") counts how many items share an order, or a seller within an order, and writes the count on every row.
  • Missing categories become "unknown". All numbers are stored as floats, so missing values (NaN) are allowed when the model is called from the endpoint later.

Build three models

Each model is a scikit-learn pipeline: preprocessing and model are saved together, so the endpoint gets one object that accepts raw features.

src/train.pylines 125–155 (condensed, comments added)
def log_target(regressor):
    """Train on log(1 + freight) because freight is very skewed; predictions come back in R$."""
    return TransformedTargetRegressor(regressor=regressor, func=np.log1p, inverse_func=np.expm1)

def make_boosting_model(args):
    preprocess = ColumnTransformer([
        ("categorical", OrdinalEncoder(handle_unknown="use_encoded_value", unknown_value=-1), CATEGORICAL),
        ("numeric", "passthrough", NUMERIC),
    ])
    model = HistGradientBoostingRegressor(
        learning_rate=args.learning_rate,        # 0.05: how big each correction step is
        max_iter=args.max_iter,                  # up to 600 trees
        max_leaf_nodes=args.max_leaf_nodes,      # 63 leaves per tree
        min_samples_leaf=args.min_samples_leaf,  # at least 40 items per leaf
        categorical_features=list(range(len(CATEGORICAL))),
        early_stopping=True,                     # stop when 10% held-out data stops improving
        validation_fraction=0.1,
        random_state=42,                         # same result every run
    )
    return log_target(Pipeline([("preprocess", preprocess), ("model", model)]))
  • TransformedTargetRegressor applies log1p to the target before training and expm1 to every prediction, so you always get reais back.
  • Gradient boosting builds hundreds of small decision trees, each one correcting the errors of the trees before it. OrdinalEncoder turns state and category names into numbers that the trees split on directly.
  • The linear model (make_linear_model) one-hot encodes the categories, fills missing numbers with the median, scales them, and fits a Ridge regression. The baseline is DummyRegressor(strategy="median").

Split by time, train, compare: main()

src/train.pylines 215–239 (condensed)
with mlflow.start_run():
    mlflow.log_params({k: v for k, v in vars(args).items() if k not in ("data", "output_dir")})

    df = build_dataset(args.data)
    cutoff = pd.Timestamp(args.test_start)                    # 2018-06-01
    train, test = df[df["purchase_timestamp"] < cutoff], df[df["purchase_timestamp"] >= cutoff]

    candidates = {
        "baseline": DummyRegressor(strategy="median"),
        "linear": make_linear_model(args.ridge_alpha),
        "boosting": make_boosting_model(args),
    }
    for name, model in candidates.items():
        model.fit(X_train, y_train)
        results[name] = evaluate(y_test.to_numpy(), model.predict(X_test))
        mlflow.log_metrics({f"{name}_{metric}": value for metric, value in results[name].items()})
  • mlflow.start_run() opens a tracked run. In Azure ML it attaches to your job automatically, so every log_param and log_metric appears in studio.
  • evaluate() computes MAE (average error in R$), RMSE (punishes big misses), R² (share of variation explained) and within_5_brl (share of predictions within R$5).
  • Metric names get the model as prefix, e.g. boosting_mae, so all three models can be compared side by side.

Deploy the model as an online endpoint

15–20 minutesBilled every hour while it exists

An endpoint is the HTTPS address and its keys. Behind it runs a deployment called blue: a VM that loads your registered model and answers requests through a scoring script.

deploy/score.pycondensed
def init():                                   # runs once, when the container starts
    global model
    path = _find_model_file(os.environ.get("AZUREML_MODEL_DIR", "."))
    with open(path, "rb") as f:
        model = cloudpickle.load(f)

def run(raw_data):                            # runs for every request
    try:
        body = json.loads(raw_data)
        records = body.get("input_data", body) if isinstance(body, dict) else body
        features = _prepare(records)          # checks required fields, fills in defaults
    except (ValueError, TypeError, json.JSONDecodeError) as error:
        return {"error": str(error)}
    predictions = model.predict(features)
    return {"freight_value_brl": [round(float(p), 2) for p in predictions], "model": "olist-freight-cost"}
  • AZUREML_MODEL_DIR is set by Azure ML to the folder where your registered model is mounted.
  • _prepare() uses the same feature lists as train.py. It requires eight fields and fills in the others: volume from the dimensions, same state from the two states, item counts = 1, current month.
  • Bad input returns a helpful {"error": …} message instead of crashing.

    if seller_state == customer_state:

Self-check

Check your understanding

1. Why is the dataset uploaded by a script and not by Bicep?

Bicep runs inside Azure Resource Manager and cannot read files on your laptop. Bicep creates resources (control plane); the Azure ML CLI puts content into them (data plane).

2. Why split train and test by date instead of at random?

In real use the model predicts future orders. A random split lets the model see orders from the same weeks as the test set, which makes the score look better than it will be in production.

3. Why does train.py train on log(1 + freight)?

Freight is very skewed: most items cost around R$16 but a few cost hundreds. On a log scale the errors of cheap and expensive items are more comparable, which makes training more stable. The downside: predictions for expensive items are pulled down.

4. Why compare against a baseline that always predicts the median?

A metric on its own means little. The baseline shows how much the model actually learned: here, a 44% lower error.

5. Why does score.py use the same feature lists as train.py?

The model only understands the columns it was trained on, in the same format. If the endpoint built different features, predictions would be wrong without any error message (training/serving skew).

6. Where does your endpoint key come from, and where should it live?

Azure generates it when you create your endpoint. You fetch it with your own login (get-credentials) and keep it only in app/.env on your computer: never in code, git, chat or screenshots.

7. The training VM is deleted after the job. Why is the endpoint VM not?

Training is a one-off batch task. An endpoint must answer requests at any moment, so its VM runs all the time, and you pay for it until you delete the endpoint.

Words used in this lab

Glossary

Resource group
A folder for related Azure resources. Delete it and its contents go with it.
Bicep / what-if
Azure's infrastructure language, and its preview of the changes a deployment would make.
Compute instance
Your personal cloud workstation with Jupyter and VS Code.
Serverless compute
A VM Azure ML creates for one job and deletes afterwards.
Data asset
A named, versioned reference to data, e.g. olist-ecommerce-raw:1.
Pipeline (scikit-learn)
Preprocessing steps and a model chained into one object that is trained and saved together.
Gradient boosting
Many small decision trees, each one correcting the errors of the previous ones.
MAE / RMSE / R²
Average error, error that punishes big misses more, and share of variation explained.
MLflow
Open-source tool for logging runs and packaging models; built into Azure ML.
Model registry
Where trained models get names and versions in the workspace.
Online endpoint / deployment
The HTTPS address with keys, and the VM running one model version behind it.
Scoring script
score.py: init() loads the model, run() answers each request.
Gradio
A Python library that turns functions into a small web app.
.env file
A private, local file of settings and secrets, loaded as environment variables and never committed to git.
